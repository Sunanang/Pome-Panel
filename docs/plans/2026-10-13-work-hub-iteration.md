## 1. 背景和定位

Pome 定位为“随时唤出的个人工作中枢”。差异化来自唤出快、停靠稳、本机优先，以及能接住 AI 工作结果。第一轮先修复数据可靠性和表达问题，再交付可回看的最小 AI 完成收件箱。范围到此冻结，不增加独立聊天页、插件市场、多人协作、复杂项目管理或知识图谱。

当前已确认：首页 Markdown 预览存在叠字；笔记多个保存路径静默保留前 200 条；备份入口只导出待办，未配对时会导出空数据；录音元数据与音频的同步结果没有充分区分；密钥文案与 NAS 同步能力不一致。AI 完成事件已有最近 20 条内存历史及桥接入口，但缺少持久化和回看界面。

产品现有行为以 [README](/Users/lando/coding/Pome-Panel/README.md) 为事实来源，开发约束以 [AGENTS](/Users/lando/coding/Pome-Panel/AGENTS.md) 为准。本文件描述本轮要实现的目标，不表示功能已经存在。实现完成后再更新 README；验收未完成时明确标为“未验证”。

## 2. 交付安排和共同边界

| 交付 | 目标 | 与另一交付的关系 |
| --- | --- | --- |
| A：可靠性修复 | 保存不丢资料；备份能恢复；恢复与同步的影响可理解、可确认、可回退 | 不等待收件箱完成。 |
| B：最小 AI 完成收件箱 | 完成事件重启后仍可查看，已读与去重稳定，关联窗口可安全回看 | 不以 A 的备份、NAS 接口或导航改造作为技术前置。 |

共同边界：

- 保留 Electron + 原生 HTML/CSS/JavaScript 架构，不新增渲染构建步骤。
- 保留四边吸附、仅收起可拖动、从停靠边展开、固定页面工作区和现有窄屏规则。几何仍集中在 `platform.js`。
- 保留待办 `notch-todo-data` 的 P0–P3 结构及已有分类名称键；新增元数据采用兼容扩展，不改写历史业务数据。
- 主进程负责文件、系统能力、凭据和持久化；渲染层经 `preload.js` 的受限 IPC 使用这些能力。
- 剪贴板默认关闭且不新增全局剪贴板快捷键。摄像头、麦克风仍只在用户主动操作后启用，并按现有规则释放。
- 本机工作区继续是用户内容落点；`sync.db`、设备令牌、证书信任和运行期窗口 ID 不等于用户可移植内容。
- 首页布局保持本机专属，不加入 NAS 同步。Windows 原生能力继续默认关闭；未启用时不加载 koffi，不覆盖用户保存的组件偏好。
- 不重置现有工作树，不撤销此前已完成的修复。实现前先核对当前代码，不假定评审时的行号或状态始终不变。

### 3.2 明确不做

- 大文件音频续传、扩大音频同步上限、重写录制链路、录音逐段落盘和崩溃恢复。
- 回收站、统一删除保留期、自动合并编辑器、专门冲突处理页面或通用历史版本浏览器。
- 跨机密钥导出/导入、新密码管理器能力、密钥类型重构或新增应用解锁系统。
- 多种备份格式、定时备份、云备份或通用备份管理中心。
- 资料库导航合并、统一搜索、场景预设、结束今天及新的 AI 服务。
- 为绕过限制自动启用明文 HTTP、扩大证书信任或关闭 TLS 校验。

“明确不做”不免除数据保全要求。未实现的能力应禁用并解释原因，不能通过默认覆盖、忽略错误或显示成功替代。

### 3.3 数据约定：本机备份 v1

备份使用单文件 ZIP 容器，扩展名 `.pome-backup.zip`；使用可支持实际媒体大小的实现，读写媒体不得一次性全部转成内存 Base64。备份格式版本独立于应用版本，第一版为 `formatVersion: 1`。

容器至少包含：

```text
manifest.json
manifest.sha256
data/workspace.json
media/recordings/...
media/clipboard-images/...
```

`data/workspace.json` 保存白名单内业务存储键的既有结构，不借备份重写 P0–P3 或其他集合模型。媒体引用在备份和新写回数据中使用 `/` 分隔的相对路径。

| 内容 | 第一版处理 |
| --- | --- |
| 待办、分类名称 | 包含真实当前内容；不依赖 NAS 投影是否可用。 |
| 首页随笔、归档笔记、笔记选择信息 | 包含；选择信息只恢复可验证存在的对象引用。 |
| 链接、分组、常用指令 | 包含既有内容和组织关系。 |
| 剪贴板历史、收藏及其引用图片 | 包含已经保存的内容；导出不得开启采集或读取新的系统剪贴板内容。 |
| 录音元数据、转写、已保存音频 | 包含本机已有内容；大于 NAS 同步上限的本机音频仍应能备份和本机恢复。 |
| 密钥、AI Key、Cursor/Codex Token、设备令牌 | 不包含；不将明文或系统加密凭据混入普通备份。预览明确显示排除项。 |
| 配对关系、账号同步密钥、证书信任、同步游标、待发送队列、`sync.db` | 不包含、不从旧备份恢复。 |
| 停靠坐标、首页布局、快捷键和系统开关、当前数据目录 | 本轮备份不替换这些本机设置；预览说明保留当前值。 |
| AI 完成收件箱 | B 的本机运行记录，本轮不纳入 A 的资料备份或 NAS 同步。 |

`manifest.json` 必须记录格式标识、格式版本、应用版本、创建时间、备份 ID、包含与排除的内容，以及以下信息：

- 每个集合的条数；子结构分别记录，例如待办 P0–P3 条数、笔记归档条数和首页随笔是否包含、链接及分组条数。不要用同一含糊总数混算分组和条目。
- 每个数据文件、媒体文件的容器内相对路径、字节数及 SHA-256。
- 明确的媒体引用和缺失/未保存音频状态。没有音频引用的转写记录，不冒充已有完整音频。
- `manifest.sha256` 校验 `manifest.json` 的实际字节；其余文件按 manifest 校验。校验和不依赖平台换行或重新序列化的 JSON。

导出读取的是一致的本机快照：先完成当前编辑及业务状态落点，再固定内容版本和媒体引用。导出期间发现被引用文件变化、丢失或读取失败，应失败并说明对象，不产生看似完整的备份。最终文件先写临时路径，验证后再作为成功备份交付；失败不覆盖已有文件。

恢复前依次检查容器、支持的格式版本、存储结构、路径、引用、集合条数、文件大小及哈希。拒绝路径穿越、绝对路径、重复目标和链接跳转；不能向工作区外写入。媒体缺失或任何校验不一致时拒绝恢复，明确显示文件/集合及原因。未知版本提示不支持；第一轮只承诺 v1，不能将“识别版本号”宣传成已支持历史格式迁移。

恢复预览显示：来源时间和版本、各集合新增/替换/删除数、媒体数量及大小、排除项、当前备份可否恢复、NAS 配对状态及恢复后暂停说明。第一轮只提供整份备份替换受管理资料，不增加逐条挑选、增量导入或跨格式导入。

校验及预览不修改当前资料。用户确认后，先创建并验证当前本机资料快照；失败则禁止恢复。待写入内容在暂存区准备完成后整体应用，并刷新 LocalStorage、`workspace.json` 与媒体引用。不能留下部分集合新、部分集合旧的状态。中断或写入失败应回退，保留恢复前快照和操作结果；再次启动时识别未完成恢复，先完成回退/恢复处理再允许同步。被本轮普通备份排除的凭据和本机设置保持原值。

### 3.4 同步暂停与恢复后的 NAS 对齐

暂停状态持久化在本机控制存储，独立于可恢复资料，并绑定当前工作区、账户及恢复操作。渲染层布尔值和一次弹窗不能作为唯一记录。

已配对设备在应用恢复内容前，先持久化暂停并阻止新的待办和工作区资料同步；已经在途的读写必须完成结算或取消，不能在恢复后再写入旧投影。NAS 可达性探测可继续，但不推送、拉取应用资料。暂停期间本机修改正常保存；不得丢弃修改，也不得直接恢复执行旧的待发送队列。

| 状态 | 用户可见行为和转换 |
| --- | --- |
| 未配对恢复成功 | 本机继续使用，不要求连接 NAS；后续首次配对遵循经过验证的既有迁移流程。 |
| 已配对恢复成功 | 保持“同步已暂停，恢复后的资料尚未与 NAS 对齐”，首页/状态入口和设置均可重新打开对齐决策。 |
| 稍后处理、取消、网络失败、执行失败 | 继续保持暂停；重启不解除。 |
| 用本机覆盖 NAS | 生成最新影响预览、确认、创建并验证 NAS 快照，再提交受保护的覆盖操作。只有成功结果已核验且本机状态已结算，才解除暂停。 |
| 先拉取再合并 | 只有经过本节和冲突场景验收的实现才可执行；未验证时禁用，说明原因，并提供稍后处理。不能默默执行普通同步。 |
| 手动解除暂停 | 重新展示最新影响范围与将采用的已验证策略；确认后按该策略结算，再解除暂停。不能绕过预览、快照要求或未验证能力。 |

对齐预览覆盖暂停期间所有新增、编辑、删除和媒体变化，明确显示其他设备的影响。预览至少绑定本机业务内容版本/摘要、媒体清单摘要、NAS 账户及版本、覆盖集合和当前配对身份。预览后任一相关内容变化、换账户或换工作区，原确认失效，必须重新预览、重新确认。

“用本机覆盖 NAS”仅覆盖本轮普通备份管理的资料集合及媒体关系；NAS 独有资料是否删除及数量必须逐集合明确显示。密钥、AI 凭据、设备令牌、配对关系、账号同步密钥和其他账户不在该操作覆盖范围内。不能把“不在本机普通备份内”理解为“需要删除 NAS 上的全部内容”。

恢复后的本机状态、旧同步基线和旧队列由已验证策略重新结算；不能原样复用旧游标与队列，也不能直接清空后假装所有资料已同步。执行期间出现的新本机编辑必须保留并标为后续待同步，不能误归入已完成覆盖。最终确认版本与 NAS 提交版本之间需要并发保护；发现其他设备上传新变更就停止提交并重新预览，不接受先覆盖再告知。

第一轮不为了完成覆盖而绕过现有媒体上限。若目标资料无法完整表达或提交，阻止相关覆盖并说明原因，保持暂停；本机恢复和本机使用仍可完成。不能因为本机音频未上传，删除 NAS 上原本可用的音频。

### 3.5 NAS 快照、覆盖与回退

这是 NAS 端能力，必须有真实持久化、验证和回退测试，桌面提示或临时内存副本不算完成。

- 快照绑定账户、操作 ID、源 NAS 版本、创建时间、集合条数、文件/实体校验及覆盖范围。包含该账户可回退的业务资料及媒体；已有密钥密文可以作为不透明业务数据保全，不转成明文、不替换账号同步密钥。
- 快照创建、源版本校验与覆盖提交需要一致的并发约束。预览后 NAS 变化则要求重新确认；提交时不能覆盖后来上传的数据。
- 快照必须成功落盘、重新读取并通过校验；缺接口、旧 NAS 版本不支持、空间不足、权限失败或校验失败时禁止覆盖，继续暂停。
- 覆盖按整个已确认操作结算。分批传输不等于允许部分对用户生效；最终提交失败时保留原 NAS 资料和快照，不允许某些集合已替换、其他集合仍旧。
- 操作有幂等标识。网络超时、重复确认、重启重试能够查询同一操作结果；不能重复删除、重复创建同一快照或凭猜测解除暂停。
- 保存可定位的快照 ID 与操作结果，并提供本次覆盖对应的明确回退路径；第一轮不增加通用快照管理页面。
- 回退前检查当前影响并确认；回退应用业务内容作为新的服务器变更，版本继续递增。不能直接回退整个 `sync-state.bin`、服务器版本号、游标、请求去重结果、配对关系或设备令牌。
- 首轮不静默过期或删除这些恢复保护快照。清理策略不在本轮实现；容量不足时明确失败，不能以删除唯一保护副本换取覆盖成功。

NAS 无此能力时，本机备份与恢复仍可交付，但覆盖入口必须不可执行。NAS 覆盖能力的验收单独标为未完成，不以“按钮已禁用”代替完成；上线时明确支持的 NAS 版本。

### 3.6 待办和笔记冲突约定

测试应从实际桌面同步、协议和 NAS 实现出发，不能只写一份理想规则。文档中的规则与运行结果不一致时修正实现，不能用描述掩盖内容丢失。

**待办：** P0–P3 模型不变；首次配对的整端选择和日常同条待办冲突分开说明。第一轮不引入字段级自动合并引擎。以服务器接受变更的版本顺序结算同一待办的正常更新，写清完成状态、标题、截止时间的最终版本及远端删除对旧待发送更新的处理，不能仅用不同设备的本地时间比较新旧。已知远端删除应取消旧基线产生的更新，不由普通重试复活同一 ID。两个设备的实际顺序、结果和剩余队列必须在测试中可观察。

**笔记：** 普通远端更新、自己推送的回声、双端分歧、删除与未同步编辑必须区分。确认两端保留不同修改时，将另一版本保存为独立笔记，不静默覆盖正文。远端删除与本机未同步编辑相遇时，原笔记可以按删除结算，但未同步正文须以新的笔记 ID 保留，不能复活原 ID。

冲突副本放回现有笔记列表，显示 `标题（冲突副本 · 设备名 · 时间）`。设备不可识别时写“未知设备”；时间注明生成时间，不推断来源设备的编辑时间。用户可以正常查看、编辑和删除，不增加专门冲突处理页面。

冲突副本记录最初笔记 ID、原始标题、参与版本/内容摘要、来源设备、生成时间及稳定去重标识。它作为普通笔记参与 NAS 同步；元数据必须经导出、恢复、归一化和同步保留，不能因为现有白名单归一化而丢失。使用兼容字段或等效元数据承载，不破坏旧笔记。

副本再次发生并发修改时，仍保留不同版本，并统一关联最初笔记；从原始标题生成平铺名称，不反复追加“冲突副本”。去重基于版本和内容关系，不基于标题或生成时间。重复拉取、断线重试、自身回声和两端对同一分歧的处理不会生成重复副本；不同修改不能被误去重。

### 3.7 同步结果与文案

能力说明与当前结果分开：

| 层次 | 示例 |
| --- | --- |
| 保存位置/能力 | 本机保存；支持 NAS 同步；本机专属；本机加密保存、启用后可加密同步。 |
| 当前结果 | 未启用同步；同步已暂停；待同步；传输中；已同步；部分完成；失败。 |

## 4. 交付 B：最小 AI 完成收件箱

### 4.1 范围

- 接收现有 `codex`、`claude`、`gpt` 本机完成事件，先可靠保存，再更新列表和展示提醒。
- 最近 20 条作为默认展示数量，可以查看更多；增加未读状态、已读状态及回看入口。
- 首页增加紧凑的“最近完成 / 待查看”入口，打开列表或浮层；不新增顶层页签，不改整套首页布局。
- 展示来源、标题、已有项目文本、接收时间和已读状态；已有项目文本只作为信息，不增加项目管理能力。
- 对仍可关联且平台允许的窗口提供返回；无法定位时说明原因，记录仍可查看。
- 持久化去重信息和已读状态，正常重启不重复添加或重新变未读。

### 4.2 明确不做

- 实时 Agent 运行状态、进度推断、项目分组、全文搜索、任务编排、自动发送后续提示或执行命令。
- NAS 同步、跨设备收件箱、云端会话事件、子代理完成提醒或来源白名单扩展。
- 自动创建待办、AI 结果解析、聊天界面或新的全局快捷键。
- 取消 Windows 原生能力限制，或为返回窗口自动启动程序、打开任意路径/URL。
- 因持久化完成事件而改变现有通知窗口不抢焦点、队列上限或待办提醒规则。

### 4.3 数据和存储约定

收件箱是本机运行记录，存放在 `userData` 下独立的受版本管理存储，不放进资料 LocalStorage、可恢复工作区、NAS 集合或 A 的普通备份。更换工作区不丢掉已有记录；能够显示接收时已有的项目上下文，但不把路径变为可任意执行的入口。

记录至少包括稳定记录 ID、来源、来源任务标识（有则保留）、标题、已有项目文本、接收时间、已读时间、去重信息及可选窗口关联线索。使用主进程接受的规范化事件，不保存原始任意请求体、凭据或不需要的窗口内容。

存储版本从 v1 开始；写入应原子，事件成功落盘后才对外确认接受并展示通知。写入失败不得返回成功或只弹通知不留记录；既有记录损坏时保留原文件并提示，不能清空后假装全新。失败重试和重启后的接受行为有明确测试。

去重沿用来源和任务身份，并保持现有去重窗口语义；不能永久按 `taskId` 去重而吞掉后续真实完成。无任务标识时使用规范化内容及既有时间窗口作为回退。同一事件重试不产生新记录、不重新变未读、不更新原始接收时间。窗口过后实际新发生的完成事件仍可形成新记录；界面不把无法区分的重试与新事件包装成绝对识别。

接收事件不等于已读。查看记录详情或用户主动标记时写入已读时间，单纯打开列表不将所有条目标为已读；返回窗口失败不妨碍用户查看事件信息。已读状态与去重标识一起可靠保存。

### 4.4 展示上限和保留规则

第一版默认展示最近 20 条，查看更多采用分页或等效增量加载，不截断持久化数据。

已读记录以首次标记已读时间为保留起点，保留 30 天；时间到期后可以自动清理。未读记录不按该规则删除，本轮不额外设置未读条数硬上限。存储写入失败按错误处理，不能通过悄悄丢弃未读记录腾空间。第一版不另加条数清理规则，避免时间和数量规则含糊叠加。

界面固定说明：`默认显示最近 20 条，可查看更多；已读记录保留 30 天，未读记录不自动清理。` 去重窗口内所需信息不得因清理丢失。重复查看或重复事件不延长同一记录的保留起点。

### 4.5 窗口回看与平台边界

持久化窗口关联线索不等于窗口 ID 长期有效。每次返回前必须通过当前扫描缓存和平台适配器重新验证，只向既有聚焦 IPC 提交当前有效 ID。无法可靠匹配时显示“窗口已关闭或无法定位”，保留记录，不猜测、不启动新进程、不执行事件携带的路径或命令。

macOS 遵循既有辅助功能权限和最近扫描缓存规则。Windows 原生能力未启用或不可用时，不调用原生聚焦，也不自动开启；列表可查看、记录可标已读，返回窗口明确说明能力不可用。系统通知点击在默认 Windows 模式仍按 README 规则处理，不因新增收件箱改变现有安全边界。

## 5. 共用回归基线

### 5.1 唤出性能和可复现文件

暖唤出初始目标为 **P95 ≤ 300ms**。这是待测量的验收目标，不是当前实测值；不因首次不达标就扩大功能范围或静默调高阈值。首次启动耗时单独报告，不混入暖唤出。

实现时提供固定脚本入口及说明，例如 `scripts/check-work-hub-baseline.js`，并接入明确的执行命令。该脚本当前尚不存在，不能在实施前宣称命令可运行。测量使用隔离测试 profile、固定夹具和原始桌面运行路径，不读取真实登录态、启动麦克风/摄像头或写生产 NAS。

标准夹具固定种子和版本，至少包含 250 条笔记、200 条待办、100 个链接、20 条录音元数据及可校验的合成媒体、50 条完成事件；按 A/B 可用程度标注实际数据量，不临时删除资料来压低延迟。记录夹具哈希、媒体数量和总字节数。

固定测量步骤：

1. 记录机器型号、CPU/内存、操作系统及版本、架构、应用/Electron 版本、提交标识及工作树是否有修改、测试文件摘要、屏幕工作区、DPI/缩放、刷新率、减少动态效果设置和同步状态。
2. 屏幕保持解锁可见，应用完成初始化；暖唤出先预热 5 次，预热不计入结果。冷启动另存结果。
3. 每轮从已稳定折叠状态通过生产唤出入口触发，测 20 次；另在隔离后台同步负载下测 20 次，两组分别计算。
4. 起点为主进程接受唤出触发的单调时钟时间。终点为渲染层已显示正确页面、导航可响应且完成一个可验证输入操作后，主进程收到本轮关联确认的时间。使用同一主进程时钟计算，不直接减两个进程的 `performance.now()`。
5. 记录每次毫秒耗时及是否成功、是否超时。终点不能仅用 `show()`、IPC 已发送或 DOM 已存在代替；不要求整段装饰动画结束，但内容必须真正可交互。
6. P95 使用 nearest-rank：耗时升序，第 `ceil(0.95 × n)` 项；20 次取第 19 项。超时和失败不剔除，任一次失败都使本组失败，并保留诊断。普通和同步中两组均需满足目标。
7. 同时执行下节的 20 次展开收起位置检查。输出原始 JSON 及便于审阅的 Markdown 摘要，并记录执行命令和执行时间。

结果目录约定为 `dist.noindex/iteration-validation/<run-id>/`，包含 `environment.json`、`samples.json`、`summary.md` 以及必要日志。该目录仅保存本机验证产物，不提交生成文件；提交脚本和固定夹具定义。对外留档时显式交付这些文件，不只给出“通过”。

结果文件至少有 `schemaVersion`、文档版本、夹具版本、测量定义、各组原始耗时、失败/超时、样本数、P95、阈值、最终状态及未验证项。无法获取的机器信息标为未知并解释，不伪造；虚拟环境和真机结果分开。当前文档没有附实测结果，所有新增基线均为未验证。

### 5.4 快捷键规则

统一搜索尚未交付，但快捷键边界现在固定：保留当前可配置唤出；搜索的 Cmd/Ctrl+K、切页和快速捕获优先设计为面板内动作，不批量注册全局快捷键。A/B 只实现当前交付需要的键盘行为，不加入不存在的搜索入口。

新增浮层应遵守统一优先顺序：当前对话框/浮层先消费 Escape，然后才处理面板；输入法组合输入不被快捷键截断；关闭后焦点回到触发入口。使用平台能力决定修饰键，不能在 Windows 把 Win 键当作 Ctrl。后续搜索交付沿用这些规则。
