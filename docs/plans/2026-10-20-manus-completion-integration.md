# Manus AI 完成接入实施方案

日期：2026-10-20。状态：第一阶段代码已落地并修复审查问题；真实账号与 Windows 真机验收、第二阶段等待提醒尚未完成。第 17 节记录实际交付与测试边界。

本方案基于当前 `dev` 的代码与当日 Manus 官方 v2 文档。当前产品仍以 README 为准；本方案获准实施后再更新 README 的产品行为。旧多来源计划中“Manus 因公网 webhook 暂不接入”的技术判断由本方案修正：可使用官方 API 主动只读查询。

## 1. 推荐范围与交付顺序

第一阶段交付 Manus 完成、失败通知、首页记录、已读同步与 NAS 统一裁剪。使用现有 Manus API Key；“接收完成提醒”是本机单独开关，默认关闭。保存额度 Key 不自动开启任务读取。

第二阶段单独交付等待输入、等待选择、等待授权及自动撤销，复用 B 蓝色定稿与已有待处理存储。第一阶段遇到 waiting 只继续跟踪，不能误发完成通知。第二阶段未完成前，设置中的等待能力保持 unsupported。

第一阶段由运行中的桌面面板主动访问 Manus HTTPS API。面板退出或电脑休眠期间没有实时采集；重开后补查。NAS 第一阶段负责同步历史，不负责托管 API Key 或持续轮询。无需用户部署公网回调，也不改写 Manus 客户端配置。

交付标记先用 partial。fixture、模拟接口或 macOS 上的 Windows 预览不能提升为 verified。

## 2. 官方事实与实现决策

以下“事实”来自官方资料，“决策”是 Pome Panel 的拟定实现，不能把后者描述成 Manus 的保证。

| 官方事实 | 实现决策 |
| --- | --- |
| API Key 可访问用户全部任务；OAuth create_task 只覆盖应用创建的任务 | 首版复用 API Key，目标覆盖同账号网页、客户端及 API 的主任务；先实测可见性 |
| user.me 提供稳定的用户身份 | 用用户 ID 建立账号命名空间；更换同账号 Key 保留游标，更换账号重建基线 |
| task.list 支持分页，但排序依据是创建时间 | 新任务快查、已知活跃任务详情查询、旧任务持续分页扫描同时存在 |
| stopped 不保证后台工作已经结束 | 候选完成必须再核验 detail 与消息事件 |
| task.listMessages 有独立事件 ID | 用服务端事件身份区分回合，不用标题、接收时间或 task ID 永久去重 |
| API 有账号级、按端点计算的限流 | 使用每端点预算，重试退避，并给其他客户端留余量 |

依据：[权限与任务可见性](https://open.manus.ai/docs/v2/open-app)、[身份](https://open.manus.ai/docs/v2/user.me)、[任务列表](https://open.manus.ai/docs/v2/task.list)、[任务详情](https://open.manus.ai/docs/v2/task.detail)、[消息事件](https://open.manus.ai/docs/v2/task.listMessages)、[任务生命周期](https://open.manus.ai/docs/v2/task-lifecycle)、[限流](https://open.manus.ai/docs/v2/rate-limits)。

### 2.1 开工前必须核实的真实账号项目

1. 当前已配置 Key 是否可读取 user.me、task.list、detail、listMessages，而不只是余额接口。
2. 网页新建任务、项目内任务、API 新建任务，以及旧任务继续提问是否均可见。UI 创建任务没有 created_by_api_key 不得被排除。
3. 自然结束、手动停止、失败、等待、后台任务先后结束的实际事件排列；同毫秒事件的分页顺序是否稳定。
4. 结果消息与 stopped 事件谁先出现，后台结束是否产生新的状态事件，结果内容是否稍后才补全。
5. 消息游标是否过期、start_event_id 的实际读取方向、账号任务规模和接口延迟。

只读访问用户已经配置的 Key，不在日志或截图里显示它。不为了验证主动创建云端任务、消耗任务额度或执行授权操作；有需要时由用户正常操作来源软件，并采集对应只读样本。样本落盘前去除姓名、邮箱、正文中的秘密和可下载附件地址。尚未观测到的失败或后台场景继续标记为未验收。

若关键事件不足以可靠区分取消与完成，先停止该情形的完成输出，不能用“状态连续两次没变”替代证据。

## 3. 用户流程与设置文案

入口保持在“设置 → AI 提供商 → Manus”。

1. 没有 Key：显示“配置 Manus API Key 后可读取余额和接收任务提醒”。
2. 有 Key、未开启：额度功能照常；另显示“接收完成提醒”开关。
3. 开启：验证任务读取权限，建立当前账号基线，状态为“正在准备任务监听”。
4. 成功：显示“正在接收 · 上次检查 X 秒前”；辅助说明“面板运行时检查任务，关闭后将在下次启动补查”。
5. 网络错误：保留开关和检查点，显示“暂时无法检查，稍后重试”。
6. 401：显示“Key 已失效，请更新”；暂停轮询。
7. 403：显示“当前凭据无法读取任务”；不把余额查询成功当作完成接入成功，也不据此禁用仍有权限的余额功能。
8. 关闭：取消请求、停止采集，保留历史与检查点；重新开启从新基线开始，不补报用户主动关闭期间的任务。
9. 正常重启/临时断网与主动关闭不同：前两者恢复原监听连续性，后者开启新的监听时间段。

不显示安装 hook、修改配置或重启 Manus 的引导。状态不得依赖设置页一直打开。Key 改动、开关、应用生命周期统一由主进程管理。

“测试提醒”与“检查连接”分开：前者用明确标记的本地预览验证界面，不写历史/未读/NAS；后者只调用读取接口，不执行云端任务。预览成功不能显示成真实任务已验收。

## 4. 组件与数据流

```text
主进程读取加密 Key + 本机监听开关
  → Manus API 客户端（固定域名、GET、超时、限流）
  → 任务发现/活跃跟踪/旧任务扫描
  → 消息补查和状态归约
  → SQLite 事务：检查点 + 候选事件/待投递事件
  → 可信内部事件入口
  → 现有收件箱：先落盘、稳定身份去重
  → 现有通知调度器 + 首页 + NAS 同步
```

新增模块拟定为 `manusApi.js`、`manusCompletionService.js`、`manusCompletionStore.js`、`manusCompletionAdapter.js`。主进程只负责启动/停止、凭据访问、IPC 与调用现有通知流程。模块注入 fetch、时钟、调度器和存储，便于测试。

现有 `manus-usage.js` 保留其余额语义和缓存；共用网络代码如需提取，单独回归余额请求、凭据切换和错误缓存。完成查询不能把额度缓存当作任务缓存。

### 4.1 可信云端入口必须显式区分

当前 `aiEventPolicy.js` 会过滤远端/云端事件，这是现有来源的产品边界。Manus 是明确的云端例外，不能整体移除过滤。

增加仅供主进程调用的注册入口，调用上下文绑定 manus 官方只读适配器。HTTP、renderer 和 NAS 传入的 payload 无法通过填写 trusted、surface 或 adapter 字段取得此权限。`/notify/manus` 首版不作为外部接入入口；支持 Manus 历史不等于开放该 HTTP 端点。现有 hook 来源白名单需从“支持历史的来源”中独立出来。

官方客户端返回的数据也仍按不可信输入做字段、长度、类型和时间检查。unknown 状态不兜底为 completed。

## 5. 接口调用契约

全部固定使用 `https://api.manus.ai/v2/`，认证头只由主进程注入 `x-manus-api-key`。这里的“只读”指面板只调用读取接口，API Key 本身具有更广权限，不能宣传成官方颁发的只读 Key。不从配置接受任意任务 API baseUrl；禁止重定向，防止 Key 被带到其他域名。

| 接口 | 使用时机 | 关键要求 |
| --- | --- | --- |
| GET user.me | 开启、凭据变更、需要重新确认账号时 | 只持久化派生账号键，不保存邮箱/头像 |
| GET task.list | 新任务发现、完整目录扫描 | limit=100，scope=all，order=desc，include_deleted=true；消费 has_more/next_cursor |
| GET task.detail | 活跃任务跟踪、候选结束复核 | 严格检查顶层 task；不能按 list 的 data 结构解析 |
| GET task.listMessages | 变化任务增量补查 | verbose=false，分页补齐到已处理事件边界；只提取需要的字段 |

不带 api_key_id 或 oauth_client_id 过滤，避免漏掉用户在 UI 中建立的任务。读取列表后只允许已识别的 standard/project 主任务，排除 agent_subtask；新未知任务类型暂不发提醒。

任务列表时间按秒解析，消息事件时间按毫秒解析；内部统一毫秒。不能对两个接口套同一份时间转换，也不能使用本地接收时间伪造服务器完成时间。

默认单请求超时 15 秒、所有后台请求总并发最多 2、每个任务同一时刻最多一个补查。建议限制单响应 2 MiB；超限时保留游标、降低分页大小重试，仍超限则明确展示读取失败，不跳过该页。每轮调用可取消，Key/账号变更后旧请求结果不得落入新账号。

## 6. 调度、旧会话与延迟

以下都是产品初始参数，可通过真机测量调整，不是官方服务承诺。

| 通道 | 初始策略 | 目的 |
| --- | --- | --- |
| 新任务发现 | 有活跃任务每 15 秒检查首页，无活跃任务每 60 秒 | 尽快发现新任务；独立运行，不等待全量扫描结束 |
| 已知 running / 等待 / 后台仍在运行 | 目标每 15 秒复查；受总预算限制按公平队列排队 | 追踪已知任务，不因创建时间较早而丢失 |
| 所有旧任务目录扫描 | 启动后开始，完成后约 5 分钟再开始；跨 tick 保存分页进度 | 发现已经结束的旧会话重新运行，以及页外的新变化 |
| 冷任务消息抽查 | 持续公平分配剩余消息预算 | 兜底 updated_at 秒级精度、仅消息变化或状态快进快出的情形 |
| 恢复网络/唤醒 | 随机短延迟后检查活跃任务并恢复扫描 | 避免唤醒时请求并发激增 |

官方当前 detail/list/listMessages 各为 100 次/分钟，同账号其他 Key 也共享额度。面板自身先设每端点每分钟 20 次预算，保留余量；每个请求都计数，分页和重试不能绕过预算。大量活跃任务时采用公平轮询并显示延迟，不承诺所有任务始终 15 秒内发现。

对于 N 条任务，单次目录至少需要 ceil(N/100) 次请求。若首页查找占每分钟 4 次，留给目录的预算最多 16 次/分钟；这只是网络正常时的吞吐估算，不能把“每隔 5 分钟开始扫描”描述成“所有旧任务最多延迟 5 分钟”。冷任务消息抽查还需要单独预算。

列表按创建时间排列，因此不得遇到第一个已知 task ID、旧创建时间或某个 updated_at 就提前停止整轮扫描；也不能只保留前 100 个任务作为监听范围。目录分页期间新增/删除可能改变结果，按 task ID 合并、后续复扫对账，不声称 API 提供一致性快照。

消息补查不固定只读最近 10 条。已有事件边界时，用支持的增量起点和分页补到本轮终点，处理 inclusive 边界重复；不能同时发送 start_event_id 和 cursor。具体排序组合先由阶段 0 实测锁定。遇到相同时间戳，以服务端稳定事件顺序/边界为准，不能按不透明 ID 的字母序推断先后。

若接口事件已过期、游标无法恢复或历史不完整，显示“部分任务需要重新核验”，保留证据与检查点。有限预算下只保证已核实事件处理，不声称跨任意长离线时间仍完全无遗漏。

### 6.1 首次基线与关闭期间

首次开启先建立监听时间段和任务基线，不导入既往完成历史。运行中的既有任务纳入跟踪，之后真实结束可以提醒。

分页初始化期间的边界必须单独测试：对首次看到的已结束任务，读取其终止事件，区分开启前已经结束和开启后才结束；不能因为它第一次出现在扫描中就直接通知。需要可靠的服务端事件时间与设备时差核验；不能假定所有响应都有 Date 头。若时差/事件边界无法确认，初始化阶段的模糊事件只作核验候选，明确显示监听尚未准备完成，不悄悄宣称完整覆盖。

新任务在两次查询之间直接从创建跑到结束，即使面板没看到 running，也可根据基线之后的完整事件历史确认并接收。老会话在两次查询之间完成多轮，则逐个核实新的终止事件，不能只比较最后一个状态。

主动关闭后再开启建立新时间段，不追溯关闭期间；正常退出后重启仍恢复原检查点，二者不得共用“清空状态”的实现。

## 7. 状态机与完成判定

内部状态建议为：initializing、running、waiting、background、verifying、completed、failed、cancelled、deleted、unknown。它们是监听内部状态，不能直接扩展成完成历史中的新状态。

| 读取证据 | 处理 |
| --- | --- |
| running | 跟踪，不写完成记录 |
| waiting | 跟踪，不作为 completed/failed；第一阶段没有等待气泡 |
| stopped 且后台标记为 true | 进入 background，继续查询 |
| stopped 且后台标记明确 false，有本回合终止证据 | 进入 verifying，核验是否自然结束 |
| 后台标记缺失 | 不当作 false；继续核验并标注旧记录/信息不全边界 |
| 本回合有 user_stop 或可靠取消证据 | cancelled，只推进控制状态，不弹成功或失败 |
| 当前任务 error，且有对应终止错误证据 | failed，写失败记录；普通过程中的 error_message 不能单独决定终态 |
| deleted | 退出跟踪、撤销未来待处理提醒；不伪造完成，也不自动删除既有完成历史 |
| list/detail/messages 状态相互矛盾 | 保留候选，稍后重试，不抢先发成功 |
| unknown / 字段非法 / 找不到回合边界 | 不发完成，报告受限状态 |

完成候选核验顺序：读取消息新增区间 → 定位当前回合及终止事件 → 排除用户停止/取消与仍等待情形 → 再读 detail 确认没有继续运行或后台工作 → 生成事件。

候选刚出现但结果消息尚未齐全时，建议 2 秒后复核一次。这是减少短暂不一致的缓冲，不是“2 秒没变就算完成”。如果没有稳定终止事件身份或不能证明自然结束，宁可保持待核验。后台结束后没有新 stopped 事件时，可用已核实的本回合终止 ID 作为身份；后台标记变化本身不生成第二条同回合完成。

同一任务下一轮开始必须保留已完成轮次，不覆盖上一条历史。任务重命名、分享权限变化、积分变化、结果附件格式变化，均不能成为新回合的证据。

## 8. 事件身份与内容映射

拟定原始完成身份为以下元组的 SHA-256，避免拼接歧义：

```text
["manus-completion-v1", accountKey, taskId, terminalEventId]
```

accountKey 由 user.me.user_id 派生，作用是稳定区分账号，不代表匿名化。terminalEventId 是已核实的服务端终止状态事件 ID；具体事件选择须由真实样本确认并固定，不可每次在“状态 ID/结果 ID/更新时间”之间随机回退。确实没有稳定 ID 时不启用该情形的完成通知。

同账号 Key 轮换、不同设备、不同接收时间应得到同一原始身份。同一 taskId 下一回合终止 ID 不同，应得到新身份。标题不参与去重。用户改名、刷新十次或程序重启，都不能产生新完成。

接入现有 v2 事件时：sessionId 使用任务身份，turnId 使用该回合的稳定身份，eventId 使用上述原始身份，occurredAt 使用终止事件毫秒时间；evidence 绑定已注册的官方只读适配器。completionEventId 后续按现有规范统一生成，不能先在适配器额外哈希一套、同步拉回时再无意改变原身份。

内容规则：

1. sessionTitle 优先使用安全清洗后的任务名称。
2. completionSummary 只取本回合已核实的结果文本，优先 result 类消息；不能取上一回合回答、opening/progress 或任意最后一条消息。
3. 没有结果正文时使用中英默认完成文案，titleIsFallback=true；不能拿任务提示词冒充 AI 的完成输出。
4. 不把工具参数、推理、附件下载链接、结构化结果对象或错误堆栈直接当标题。普通用户要求的 JSON 输出不一概过滤；已知机器控制对象使用明确识别规则，而非“看起来像 JSON 就删”。
5. 沿用 4096 字符摘要上限与界面截断；敏感凭据在落盘和进入同步队列前移除。无法安全确定的失败正文使用通用错误文案，不保存原始服务响应。
6. 未核实的项目名称不伪造；可以保留空 project。taskId 保留经过校验的原 ID，不能截断后拿去打开另一个任务。

## 9. 本地控制存储与崩溃恢复

建议使用已有 node:sqlite 运行能力，新增 userData/manus-completions.db；不把内部状态混入 sync.db 的同步集合，也不改 task-inbox.json 的文件职责。

拟定表：

| 表 | 核心内容 |
| --- | --- |
| accounts | 派生账号键、监听时间段、基线状态、最近成功检查时间 |
| tasks | 账号键+任务 ID、已处理消息边界、最后状态、后台标记、目录签名、待核验状态 |
| scans | 目录/消息分页进度、重试时间；不持久化正文 |
| outbox | 稳定事件身份、已清洗的最小事件、待投递/已确认 |

同一次读取产生的状态推进与 outbox 插入置于一个 SQLite 事务中。只在消息页的内容已经安全处理、候选/outbox 已持久化之后推进已处理游标。

投递顺序：事务保存 outbox → 调用现有收件箱/通知入口 → 收到持久化成功或已存在后确认 outbox。收件箱写失败不推进确认，不弹假成功；崩溃后重试使用同一身份。

这能保证可重试写入与历史去重，不应承诺“崩溃前后气泡恰好出现一次”：现有收件箱与 UI 队列不在同一事务中，在已写历史但尚未展示时退出可能没有补弹；恢复时应优先避免重复弹，而让用户从未读历史看到记录。

内部游标/去重控制信息不属于用户可见的 100 条历史。不能因完成历史淘汰了第 101 条，就删除轮询检查点，导致旧事件再次同步回来。已删除任务可压缩控制状态，但必须保留足够的扫描基线/事件边界；损坏时保留原库并暂停，不静默重建为空后回灌全部历史。

资源控制：outbox 建议上限 1000 条，达到上限先停止继续消费新事件并显示积压，待投递恢复后继续；不能悄悄删最早未投递事件。任务目录可索引分页，避免全量读入内存；不对监听任务数套用“100 条历史”限制。控制库的清理策略需要独立测试，不能默认按 TTL 删除仍可能重新运行的老任务。

## 10. NAS 同步与多设备

同步仍使用现有 aiCompletions 集合，而非新增一份 Manus 专属历史。

1. 桌面与 NAS 两份 ai-completions.js 来源白名单加入 manus，并补一致性测试。
2. 复用现有稳定完成身份、已读合并和删除标记；相同事件在两台设备采集，NAS 合并为同一条历史。
3. 所有来源合计保留最新 100 条，按现有 receivedAt 排序规则，不是 Manus 额外 100 条。补查旧事件不会私自改变已有产品排序语义。
4. 本地新增、启动加载、NAS 合并/投影都统一裁剪，淘汰需同步删除，避免离线设备把旧记录拉回来。
5. NAS 拉取已有历史不再弹气泡；本机采集的新事件才进入本机通知调度器。
6. API Key、监听开关、账号控制库、消息游标、失败响应不进入普通完成历史同步。其他设备想自行采集时需独立配置 Key 并明确开启。
7. 首版推荐一个主要设备负责采集，其他设备通过 NAS 看历史；不自动争夺采集角色。若用户同时启用两台，各自都可能弹一次，NAS 只能合并历史，不能在离线情况下保证“全网只弹一次”。
8. 需要自动选主时，另做 NAS 租约、续约、失联/切换语义，不能仅靠本机时间或最后同步设备推断主设备。首版不引入这个额外分布式协议。
9. 旧 NAS 不支持 Manus 来源时，明确提示需要升级，保留本机记录；不可把 manus 伪装成其他来源或丢弃本机 outbox。

现有同步字段已有 taskId，可以用于跨设备打开官方任务页，不必把任意 sourceUrl 加入协议。

## 11. 点击返回 Manus 与双平台

Manus 是网页任务来源。首版点击历史记录或有能力的通知时，从主进程已保存的 manus 记录读取 taskId，构建官方任务链接，再经平台打开服务交给默认浏览器。

使用已核实的 `https://manus.im/app/{taskId}` 路由，taskId 作为单个路径段编码并限制长度/控制字符。可以校验服务端 task_url 是否与固定来源、任务 ID 一致作为证据，但不原样打开任意服务器 URL。不接受 renderer/HTTP/NAS 传入的自定义协议、脚本 URL、用户名密码或任意浏览器启动参数。

不假定已安装 Manus 桌面客户端或存在稳定 deep link。浏览器需要登录时由 Manus 自身处理；面板不会把 API Key 放进 URL，也不会注入登录态。打开失败保留通知并显示可重试原因，沿用现有机制。

Windows 原生能力关闭时，通知继续遵守现有“请返回来源软件/点击仅隐藏”限制，不因 Manus 可以开网页就绕过全局策略，也不加载 koffi。历史记录的显式打开行为遵循现有历史入口策略，与通知点击能力分别验证。macOS 不以辅助功能权限作为打开网页的前提。

平台链接打开应通过适配层/共享打开服务实现；两个现有入口 tasks:open-source 与 task-notification:activate 一起接入，不只修改气泡的那一条。

## 12. 错误、取消与可观测性

| 情形 | 行为 |
| --- | --- |
| 超时、离线、DNS、5xx | 15/30/60/120 秒递增退避，最高 5 分钟并加抖动；游标不跳页 |
| 429/rate_limited | 尊重有效 Retry-After（如服务有返回）与指数退避；账号内相关请求统一降速 |
| 401/unauthenticated | 暂停任务查询，标记需要更新 Key；不无限重试 |
| 403/permission_denied | 标记任务权限不足；不自动认定余额接口也失效 |
| 单个任务 404/不可见 | 区分删除、权限变化、暂时不可见；不能据此写 completed |
| HTTP 200 但 ok=false | 按业务错误处理，不能算成功 |
| 非法 JSON/未知状态/时间戳非法 | 保留旧状态并报告异常，不用空列表覆盖基线 |
| 关闭/换 Key/换账号/退出 | AbortController 取消，增加 generation；晚到响应被丢弃 |
| SQLite/收件箱写失败 | 停止推进相应消费边界，保留原数据和待投递项 |

公开状态只包含 enabled、connectionState、lastCheckedAt、lastSuccessfulAt、activeCount、backlogCount、lastErrorCode 和扫描是否落后。任务 ID、用户 ID、正文、Key 与原始服务错误不进普通诊断日志；需要关联时使用局部派生标识。UI 不显示堆栈、内部表名或接口参数。

## 13. 第二阶段：等待提醒

第二阶段必须在第一阶段的事件边界与真实样本稳定后实施，不能只把 waiting 统一映射成“等待授权”。

1. 问题型等待且有非空选项，映射 select；明确问题但无选项，映射 input。
2. 已确认的操作批准类型映射 approve；未知类型使用“请返回 Manus 处理”的通用入口，不伪造具体授权结论。若当前协议只支持三类，则未知类型保持待核验，不强塞 approve。
3. requestId 使用任务身份与该次等待事件 ID；同一会话连续两次请求必须分别保留，不能用脱敏后正文或等待类型做指纹。
4. 只展示清洗/脱敏后的问题，授权默认通用摘要；不保存或展示工具原始参数。没有必要为通知打开 verbose 工具细节。
5. 点击返回 Manus，不调用 task.sendMessage、task.confirmAction 或其他写接口。
6. 后续已核实的继续运行、对应请求处理、取消/删除事件自动撤销；不能因断网或超时宣布已解决。
7. × 仅隐藏本次提醒；待处理仍保留，隐藏项不计可轮换的 +N。轮换与悬停复用当前调度器，等待不设倒计时。
8. 重启恢复为 unverified，待官方状态重新核验；离线时不自动重弹，不额外弹“已回答”。
9. 等待状态沿用当前本机 ai-attention.json，不参与完成历史 100 条限制或 NAS 同步。
