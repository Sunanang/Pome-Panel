## 结论：存在一处 P2 回归

`todoReminders.js` 第 48–51 行将调度列表中缺席的任务回执全部删除，但启动阶段的列表不一定已经代表真实工作区。

构造可复现场景：新浏览器存储目录中已有 `workspace.json` 和 `todo-reminders.json`。工作区快照中的任务尚未带提醒标记，但回执文件已经记录该任务/截止时间已显示过。关闭通知启动，等待异步工作区导入，再开启通知。

1. `renderer/app.js` 第 609 行在异步工作区导入完成前发出第一次调度：`items=[]`、`expectedRoot=null`。
2. 主进程接收这个临时空列表。新清理逻辑把原来 1 条回执删成 0 条并写盘。
3. 工作区导入后，该任务的 `remindedAt` 仍为 0。
4. 开启通知，任务再次弹出；见 `hydration-duplicate.png`。图中文字“已提醒任务不应再次弹出”是隔离夹具名称。

对照实验只在进程内换回 `HEAD:todoReminders.js`，其余主进程使用当前代码，不覆盖磁盘源码。相同场景下，第一次空调度保留原回执，导入后恢复正数标记，没有重复弹窗。

| 观测项 | 当前改动 | 修改前回执实现 |
| --- | --- | --- |
| 第一次调度 | 空列表、root 尚未确定 | 相同 |
| 导入后回执数 | 0 | 1 |
| 导入后提醒标记 | 0 | 恢复原标记 |

建议：仅在工作区加载完成且调度明确属于当前工作区时，才根据“缺席”清理回执；临时启动投影不能当成删除指令。增加本场景的 Electron 回归。不能只用一次 `merge([])` 单测断言清空，因为问题在真实启动顺序与异步导入之间。
